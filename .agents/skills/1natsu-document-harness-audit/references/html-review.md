# HTML レビューページの要件

検出が多い監査結果を、1件ずつ判断できる形で提示するためのページ。会話に出した表の代替ではなく補完で、表は全体の見取り図、ページは採否を決めるための場になる。

## いつ作るか

ユーザーが求めたとき。

## 成果物

1枚の HTML。**開くだけで動く状態にする。** 渡した先で install も起動も要らないため。

制約がかかるのは**完成したページの実行時**で、`<script src>` や `@import` で外部を読みに行かない状態にする。**作る過程は縛らない。** ライブラリを使ってファイルへバンドルするのは、この制約に反しない。取得できない事情があるなら自分で書けばよい。

**受け渡しの方法はこのスキルでは指定しない。** ローカルのファイルとして渡すか、HTML を扱う別の仕組みに載せるかは、このスキルの外で決まる。ここで指定すると、その仕組みが持つ取り扱いの判断を上書きしてしまう。

## 作り方

書き始める前に、この順で決める。

1. **利用できるスキルの一覧を見て、description が HTML やページの生成を扱うものを探す。** あればそれを使う
2. **無ければ自分で書き起こす**

この順を踏むのは、既にある作法と品質を捨ててゼロから書くのを避けるため。この文書が定めるのは中身の要件で、実装と体裁の作法は使うスキル側に従ってよい。

**生成を別のエージェントへ委譲できるなら委譲する。** ページの markup は使い捨てで、会話のコンテキストに残す価値がない。委譲できない実行環境なら自分で書く。

### 委譲するときの渡し方

会話の文脈を要約して渡さない。受け取った側が書き直し案を組み立て直すことになり、監査が出した結論とずれる。**検出結果をファイルへ書き出し、そのパスを渡す。**

```bash
OUT=$(mktemp -d "${TMPDIR:-/tmp}/audit-review.XXXXXX")
```

`mkdir` と時刻でパスを組み立てない。同じ秒に走ると既存ディレクトリを黙って再利用し、権限も umask 次第（実測で `drwxr-xr-x`）になる。`mktemp -d` は一意性を保証し、`drwx------` で作る。テンプレートに `${TMPDIR:-/tmp}` を明示するのは、引数なしの `mktemp -d` がサンドボックス下で書けない場所を選ぶことがあり、素の `$TMPDIR` は未定義環境でルート直下を指すため。

`$OUT/findings.md` に、ステップ4で提示した内容をそのまま書き出す（一覧表・書き直し案の現状と書き直し後・確認事項・違反として扱わなかったもの）。**行を指せる項目には対象のファイルパスと行番号を必ず入れる。** ページ側がこれを表示する要件なので、無いと委譲先が原文を取り直すことになり、まとめた行ではどの行だったのか復元できない。

渡すのは3つ。

- `$OUT/findings.md`（検出結果）
- この要件ファイルのパス
- 監査対象リポジトリのパス（原文の確認用。**読み取りのみで変更させない**と明記する）

## 規模

**レビューを1回こなすための道具であって、製品ではない。** 書く量がそのまま生成時間になり、待ち時間はレビュー開始の遅れになる。以下は作らない。

- **差分アルゴリズム**: ページを書く時点で現状と書き直し後の両方が分かっているので、追加・削除の印を付けたデータとして埋め込む。ページ側で計算しない
- **区画の切り替え**: 採否と確認事項を分ける用途だけに使う。それ以外の内容（違反として扱わなかったもの、監査の前提等）は同じ画面の節として置く
- **入力の保存、通知の表示、書き出しの複数形式**: あっても構わないが、要件ではない

要件を満たしたら止める。手が空いたぶんを装飾や機能に回さない。

## 満たすべき要件

### 総件数と内訳が最初に分かる

先頭に検出の総数と振り分けを出す（例: 全15件、うち採否12件・確認3件）。**ページ内のどこでも同じ母数を使う。** 採否のリストだけを見て「これで全部」と読める状態にしない。確認事項へ回した項目が視界から消えると、未処理のまま完了したと誤認する。

### 1件ずつ判断できる

一覧を一度に見せず、1件を1つのまとまり（カードまたは1画面）として提示する。監査結果は10件を超えることがあり、全件を同時に視界へ入れると、どれを見終わったか分からなくなる。現在位置と残件数を常に見える位置に置く。

### 現状と書き直し後の差分が読める

その項目を承認すると何がどう変わるかを、行単位の差分で示す。追加と削除は**色と記号の両方**で区別する。色だけに頼ると、色覚の条件やモノクロ印刷で区別が消える。

### 採否を選べる

各項目の状態は **未判断 / 承認 / 却下 / 保留** の4つで、初期値は未判断。この4つから1つを選ぶ操作にする（チェックボックスでは表せない。ラジオでもセレクトでも、押して切り替わる形でもよい）。

承認と却下の二値にしない。二値だと「後で決めたい」項目が却下側へ落ちる。保留は独立した状態として持ち、集計でも承認・却下と分けて数える。未判断の残数が分かるようにして、見落としたまま完了しない形にする。

一括操作は2つ用意する。

- **すべて承認**: 会話側の「全部やって」に対応する。**未判断の項目だけ**を承認へ変え、既に判断した項目は上書きしない。手で却下や保留にしたものが消えると、やり直しになる
- **すべて未判断へ戻す**: 全項目を初期値へ戻す

### コメントを書ける

項目ごとに自由記述の欄を置く。提案をそのまま採らず条件を付けたい場合（「この行だけ残して」等）に、採否だけでは伝えられない。

### 確認事項は採否と分ける

実体を確定できず確認を求めている項目は、チェックボックスでは進められない。承認欄ではなく回答欄を持つ別の区画に置く。ここを採否のリストへ混ぜると、回答がないまま承認されて、エージェントが憶測で書き換える経路ができる。監査が確定できないと判断したものを、UI の都合で確定させてはいけない。

候補を推測できるなら選択肢として出してよい。ただし自由記述を必ず併置し、候補で表せない答えを書けるようにする。**回答済みとみなすのは、候補の選択と自由記述のどちらか一方が埋まっている状態**で、両方を求めない。候補だけ、自由記述だけ、両方、のいずれでも回答として成立する。

両方が埋まっていて内容が食い違う場合の判定は、ページに持たせない。静的なページは意味の矛盾を判定できないので、無理に実装すると誤った警告か見逃しのどちらかになる。**両方を貼り戻すテキストへそのまま載せ、一意に定まるかどうかは受け取ったエージェントが判断する**（ステップ6「指示が一意に定まらない項目は実行の流れから外す」）。

### 結果をエージェントへ戻せる

**コピーできるテキスト**を出す。会話へ貼り戻すと、エージェントがそれだけで続きを進められる状態にする。含めるのは次の4つ。

- 検出の総数と内訳
- 項目番号ごとの判断（承認 / 却下 / 保留 / 未判断）
- コメントと確認事項への回答。**どの項目のものか番号で分かる形にする**
- 未回答の確認事項があるなら、それを実行しないという指示

並べ方は決めない。判断を番号の一覧でまとめると短くなり、コメントは付いた項目だけ書けば済む。番号で一意に紐づいていれば形は問わない。読むのはエージェントなので、体裁より、項目と情報の対応が曖昧にならないことを優先する。

ファイルのダウンロードを足してもよいが、それだけにしない。保存先はブラウザの設定次第で、同名のファイルがあれば別名になる。エージェントが場所を特定できるとは限らないので、テキストを貼るだけで進められる経路を必ず残す。

### 絞り込める

重要度とカテゴリで絞り込めるようにする。重要度の高いものだけ先に処理して残りを後日に回す、という進め方が現実的に多い。

### 対象箇所へ辿り着ける

各項目に対象のファイルパスと行番号を、コピーできる形で表示する。エディタを開くリンクは環境に依存するので前提にしない。

## 作らないもの

- 修正を実行するボタン。ページは判断を集める場で、実行はエージェントが承認を受け取ってから行う。ページから直接ファイルを書き換える経路を作ると、承認の記録が残らない
- サーバを立てる仕組み。ファイルを開くだけで動く形にする
