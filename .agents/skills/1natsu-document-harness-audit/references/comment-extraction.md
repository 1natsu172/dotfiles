# コード内コメントの抽出

ステップ2.5 の絞り込みで使う正規表現の、構造と限界。コマンド本体と実行時の判断はステップ2.5 にある。ここは**結果が想定と違った時に引く**ためのもの。

## 正規表現の構造

| 部分 | 役割 |
|---|---|
| `^\s*(//｜/*｜*｜#｜--｜;｜%｜<!--｜!｜(*｜{-｜=begin)` | 行がまるごとコメントの場合。行頭にだけ `!`(Fortran) `(*`(OCaml) `{-`(Haskell) `=begin`(Ruby) を許す。Lisp のブロックコメントは開きが `#|` なので `#` で足りる（閉じの `\|#` は入れない。閉じ行の日本語は下記のブロック内部行にあたり、どのみち取れない） |
| `\s(//｜/*｜#｜--｜;｜%｜<!--)` | コード行の末尾に付くコメント。記号を絞るのは、`!` を許すと `a !== b` が、`(*` を許すと式が誤ヒットするため |
| `(?-u:.)*` | UTF-8 として不正なバイトが日本語より手前にある行でも `.` が越えられるようにする |
| `[\p{Hiragana}\p{Katakana}\p{Han}]` | 日本語の判定 |

**行末コメントを落とすと取りこぼしの過半を失う。** 18言語のコーパスで測定した際、取りこぼし21行のうち11行が行末コメントだった。行頭だけに絞った版は再現率 24/45、現行は 39/45。

**文字コードの範囲で書かない。** `[ぁ-んァ-ヶ一-龠]` のような書き方は、`一-龠` が U+9FA0 止まりで CJK 統合漢字（U+9FFF まで）の末尾が切れ、半角カタカナ・`々`・`〇`・追加漢字面・`ヷヸヹヺ` も落とす。文字種プロパティならこれらをすべて拾う。

## 記号を足す・外す判断

`"` は既定で外してある（Vim script、Visual Basic）。行頭 `"` を許すと JSON・文字列の配列・複数行文字列リテラルが大量に当たるため。これらの言語が対象なら、**行頭側の集合にだけ** `|"` を足す。行末側に足すと通常の文字列が全部当たる。

同じ理由で、記号を足すときは行頭側と行末側を分けて考える。行末側は「空白に続く記号」なので、演算子や引数と衝突しやすい。

## 取りこぼすもの

**ブロックコメントの内部行**が最大の取りこぼし。記号のある行と日本語の行が別なので、行単位の一致では状態を持てず原理的に取れない。

```python
def f():
    """
    docstring の本文（この行は取れない）
    """
```

Ruby の `=begin`/`=end`、HTML の `<!-- -->`、C 系の `/* */` で `*` を伴わない内部行、Haskell の `{- -}`、Lisp の `#| |#` が該当する。**Python の docstring は日本語の説明を書く標準の場所なので、Python が主体のリポジトリでは影響が大きい**。日本語が記号と同じ行にある場合（`"""日本語の説明"""`）は拾える。

行コメント（`//` `#` 等）には該当しない。各行に記号が必要で、記号のない継続行は構文エラーになるため。

その他:

- Vim script と Visual Basic の `"` コメント（上記のトレードオフで意図的に除外）
- Fortran の行末 `!` コメント（`!=` との衝突を避けるため行末側から除外）
- Shift_JIS 等、UTF-8 と UTF-16 以外のエンコーディングのファイル
- 長音符・約物・`〆`（いずれも Script=Common）だけで構成される行（`ーーー`、`、。「」`）。文字種プロパティでも文字コードの範囲でも拾えない

## 誤って拾うもの

CSS の ID セレクタ（`#見出し {`）、シェルの長オプション（`--data "名前=太郎"`）、コメント記号を含む文字列リテラル（`"notify --to 宛先 # 宛先は必須"`）。いずれも1行読めば棄却できるので、取りこぼしより安い。

日本語を含むだけの文字列リテラル（`const msg = "配信の失敗"`）は拾わない。空白に続くコメント記号が要るため、URL（`https://example.com/ja/ガイド`）も拾わない。

`\p{Han}` は中国語も拾う。中国語のコメントが混在するリポジトリでは、これだけで日本語と判定できない。

## 言語別のパーサーを使わない理由

依存が増えるうえ、コメントを正確に切り出せても**読む量は変わらない**。費用を決めているのは走査ではなく、絞り込んだ後に読んで判断する量なので、抽出精度を上げても主因に効かない。
